# 📣 튜링 확성기봇 (Turing Amplifier Bot)

> 누구든 팀에 공유할 가치가 있는 슬랙 메시지에 **📣**를 찍으면 자동으로 수집되고,
> 매주 금요일 오후 4시 「튜링 위클리」로 발행된다.

토스의 "터줏대감 슬랙봇" 사례를 튜링에 맞게 옮긴 것. 목표는 **누군가를 찾아가 물어봐야 알 수 있던 정보의 허들을 없애는 것**이다.

## 3. 구현 — Phase 1 (현재)

서버도 Slack 앱도 없이, **스킬 + 스케줄** 조합으로 돌린다. `attendance-late-check`(출근봇)과 같은 구조다.

```
[평일 오전]  amplifier-collect
             Slack 검색 has::mega: → 리액션 확인 → 스레드 맥락 → Notion 적재

[금 15:30]   amplifier-weekly
             수집 재실행 → 이번 호 선별 → 본문 작성
             → 채널에 슬랙 "초안" 등록 → 메리에게 DM 알림

[금 16:00]   메리가 초안 확인 후 직접 전송  ← 사람이 누르는 발행 버튼
```

승인 방식으로 **슬랙 네이티브 초안(draft)** 을 쓴다. 봇이 채널 입력창에 글을 써두면 메리가 읽고 고치고 전송 버튼만 누르면 된다. 별도 승인 UI가 필요 없고, 검수를 건너뛸 수 없는 구조라는 게 핵심이다.

### 스킬

- `.claude/skills/amplifier-collect/` — 수집
- `.claude/skills/amplifier-weekly/` — 위클리 초안 생성

### Phase 1의 한계 (알고 쓸 것)

- **실시간 확인 답글이 없다.** 📣를 찍어도 봇이 바로 반응하지 않는다. 다음 수집 때 들어온다
- **운영자 권한 범위 안에서만 검색된다.** 메리가 속하지 않은 비공개 채널은 잡히지 않는다
- 슬랙 검색 인덱싱 지연으로 방금 찍은 리액션이 늦게 잡힐 수 있다 (수집 창을 8일로 넉넉히 잡아 보완)
- 발행은 봇 계정이 아니라 메리 계정으로 나간다

## 4. 구현 — Phase 2 (4주 운영 후 판단)

Phase 1로 "사람들이 실제로 📣를 찍는지"가 확인되면 정식 Slack 앱으로 옮긴다.

- 스택: Bolt for JS + Vercel Functions + Notion API + Vercel Cron (전용 레포)
- 이벤트: `reaction_added` / `reaction_removed`
- 스코프: `reactions:read`, `channels:history`, `groups:history`, `channels:join`, `chat:write`, `users:read`
- 추가되는 것: 📣를 찍는 즉시 스레드에 "수집 완료" 답글, `/확성기 미리보기`, `/확성기 제외`, 확성기봇 계정으로 발행
- ⚠️ 제약: 슬랙은 **봇이 참여 중인 채널의 리액션만** 이벤트로 보낸다. `channels:join`으로 공개 채널을 자동 참여시키고, 비공개 채널은 개별 초대가 필요하다
- ⚠️ 워크스페이스 관리자의 앱 설치 승인이 필요하다

## 7. 스케줄 (Routines) 세팅

| 이름 | cron (UTC) | KST | 하는 일 |
| --- | --- | --- | --- |
| 📣 확성기 일일 수집 | `27 0 * * 1-5` | 평일 09:27 | `amplifier-collect` 실행, Notion 적재 |
| 📣 튜링 위클리 초안 (금) | `33 6 * * 5` | 금 15:33 | `amplifier-weekly` 실행, 슬랙 초안 등록 + 메리 DM |

### ⚠️ 최초 1회 수동 작업 — 커넥터 연결

세션에서 만든 Routine에는 **Slack·Notion 커넥터가 자동으로 붙지 않는다.** 이 상태로 두면 실행은 되지만 슬랙·노션 도구가 없어 아무것도 못 한다.

claude.ai → Routines 화면에서 위 두 Routine을 열어 **Slack, Notion 커넥터를 연결**해야 한다. (출근봇 Routine과 같은 방식이다.)

### 스킬 파일 위치

Routine이 띄우는 새 세션은 기본 브랜치를 체크아웃한다. 스킬이 아직 `main`에 없다면 프롬프트에 넣어둔 대로 작업 브랜치를 받아서 읽는다. `main`에 머지하면 이 우회는 필요 없어진다.

## 9. 첫 실전 실행에서 배운 것 (2026-09-07)

저장소 소스를 연결한 뒤 첫 자동 실행에서 신규 4건이 정상 적재됐다. 그 과정에서 확인된 것들:

- **수집된 5건이 전부 비공개 채널 출처였다.** 정보가 실제로 고여 있는 곳이 비공개 채널이라는 뜻이고, 이 봇의 존재 이유이기도 하다. 대신 "비공개는 채널명을 가린다"는 초기 규칙을 쓰면 사실상 모든 항목의 출처가 사라지므로, 채널명은 노출하고 민감도는 검수에서 거르는 쪽으로 바꿨다.
- **스레드 맥락 보강이 실제로 효과가 있었다.** "AI 드라이브 배포되었습니다" 같은 한 줄 메시지도 부모 스레드를 읽어 배포 경위를 붙이니 뉴스가 됐다. 이 단계를 빼면 위클리가 맥락 없는 단문 모음이 된다.
- **Routine에는 커넥터와 저장소 접근이 별개 설정이다.** 커넥터(Slack·Notion)만 붙이면 세션은 "성공"으로 끝나지만 저장소를 못 읽어 SKILL.md 없이 돌아간다. 둘 다 필요하다.
- 슬랙 검색 결과의 `Permalink`를 그대로 쓰는 편이 직접 조립한 링크보다 정확하다 (스레드 파라미터 포함).

## 10. 봇 명의 발송과 네트워크 정책 (2026-09-07)

위클리를 **확성기봇 명의**로 내보내려면 Slack Incoming Webhook이 필요하다. Slack MCP(`slack_send_message`)는 항상 쓸 수 있지만 **운영자 개인 계정 명의**로만 나가고, 슬랙이 본인 멘션 알림을 억제하기 때문에 전사 공지용으로는 약하다.

문제는 웹훅 도메인이 클라우드 세션의 egress 정책에 걸린다는 점이다.

```
kind:   connect_rejected
detail: gateway answered 403 to CONNECT
host:   hooks.slack.com:443
```

진단은 `curl -sS "$HTTPS_PROXY/__agentproxy/status"` 로 한다. `recentRelayFailures`에 차단된 호스트와 사유가 그대로 찍힌다. 정책 거부이므로 재시도하거나 우회하지 않는다.

### 환경마다 정책이 다르다

계정에 환경이 여러 개면 네트워크 정책도 각각이다. 확인은 `list_environments`.

| 환경 | hooks.slack.com |
| --- | --- |
| `env_01KNQLFBBCUbK2iw4D3EUVCx` (Default Cloud Environment) | 차단 |
| `env_01Rk69KYRBjm3TSL3hPL81ER` (Default — trusted network access) | 열림 |

**웹훅으로 발송하는 Routine은 열린 환경에서 만들어야 한다.** 차단된 환경에 만들면 실행은 "성공"으로 끝나면서 발송만 조용히 실패한다.

### 출근봇이 웹훅으로 잘 도는 이유

그 작업은 클라우드가 아니라 운영자의 맥에서 돌기 때문이다(스킬이 `/Users/mary/Desktop/...`에 CSV를 쓴다). 로컬에서 된다고 클라우드에서도 된다는 뜻이 아니다 — 새 봇을 만들 때 가장 걸리기 쉬운 함정이다.

### 연결 테스트는 GET으로

슬랙 웹훅은 GET에 대해 메시지를 게시하지 않고 400만 돌려준다. 채널에 아무것도 올리지 않고 터널만 확인할 수 있다.

```
curl -sS -o /dev/null -w '%{http_code}\n' <webhook_url>
```

`CONNECT tunnel failed, response 403` → 아직 차단. 정상 HTTP 코드 → 열림.
