## 3. 구현 — Phase 1 (현재)

서버도 Slack 앱도 없이, **스킬 + 스케줄** 조합으로 돌린다. `attendance-late-check`(출근봇)과 같은 구조다.

```
[평일 오전]  amplifier-collect
             Slack 검색 has::mega: → 리액션 확인 → 스레드 맥락 → Notion 적재

[금 15:33]   amplifier-weekly
             수집 재실행 → 이번 호 선별 → 본문 작성
             → 검수용 웹훅으로 메리 DM에 본문 발송  ← 자동 실행은 여기서 끝

[이후]       메리가 읽고 "보내줘"  ← 사람이 누르는 발행 버튼
             → 발행용 웹훅으로 채널에 확성기봇 명의 발행
```

승인 방식은 **DM 검수 → 사람의 "보내줘" → 채널 발행** 2단계다. DM에는 채널에 나갈 본문을 **한 글자도 바꾸지 않고** 그대로 보낸다. 보이는 그대로가 나가는 그대로여야 검수가 검수가 된다.

초기에는 슬랙 네이티브 초안(draft)을 쓰려 했으나 폐기했다. 그 채널에 이미 초안이 하나라도 있으면 새 초안이 **조용히 실패**한다 — `draft_id` 없이 성공처럼 끝나서, 봇은 올렸다고 보고하는데 메리 화면엔 아무것도 없다.

- `.claude/skills/amplifier-collect/` — 수집
- `.claude/skills/amplifier-weekly/` — 위클리 초안 생성

## 4. 구현 — Phase 2 (4주 운영 후 판단)

Phase 1로 "사람들이 실제로 📣를 찍는지"가 확인되면 정식 Slack 앱으로 옮긴다.

- 스택: Bolt for JS + Vercel Functions + Notion API + Vercel Cron (전용 레포)
- 이벤트: `reaction_added` / `reaction_removed`
- 스코프: `reactions:read`, `channels:history`, `groups:history`, `channels:join`, `chat:write`, `users:read`
- 추가되는 것: 📣를 찍는 즉시 스레드에 "수집 완료" 답글, `/확성기 미리보기`, `/확성기 제외`, 확성기봇 계정으로 발행
- ⚠️ 제약: 슬랙은 **봇이 참여 중인 채널의 리액션만** 이벤트로 보낸다. `channels:join`으로 공개 채널을 자동 참여시키고, 비공개 채널은 개별 초대가 필요하다
- ⚠️ 워크스페이스 관리자의 앱 설치 승인이 필요하다

### ⚠️ Routine에는 서로 **독립된 설정이 3개** 있다

셋 다 claude.ai → 루틴 화면에서만 설정되고, **각각 따로 조용히 실패한다.** 하나만 빠져도 세션은 "성공"으로 끝나므로 실행 이력만 보면 멀쩡해 보인다.

| 설정 | 없으면 | 증상 |
| --- | --- | --- |
| 커넥터 (Slack·Notion) | 도구 자체가 없음 | 아무것도 못 하고 끝남 |
| 저장소 소스 | SKILL.md를 못 읽음 | 절차 없이 맨몸으로 돌아감 |
| 환경변수 (웹훅 URL) | 발송 경로가 없음 | 본문을 다 만들고도 못 보냄 |

**저장소 소스**는 두 Routine 모두 `gomarygo/turing-ops`여야 한다. 프롬프트에 쓰인 경로와 실제 체크아웃이 어긋나면 파일을 못 읽는다.

**환경변수** — 웹훅 URL은 자격증명이라 저장소에 두지 않는다(GitHub 시크릿 스캐닝이 푸시를 거부한다). 두 Routine 모두에 넣는다.

| 변수 | 용도 |
| --- | --- |
| `AMPLIFIER_DM_WEBHOOK_URL` | 메리 DM 검수용 |
| `AMPLIFIER_WEBHOOK_URL` | `#튜링_회사운영_및_일반업무` 발행용 |

웹훅은 각각 **채널이 고정**돼 있어 payload의 `channel` 필드로 바꿀 수 없다. 바꿔 쓰면 검수본이 전사에 나간다.

### 스킬 파일 위치

Routine이 띄우는 새 세션은 기본 브랜치를 체크아웃한다. 스킬이 아직 `main`에 없다면 프롬프트에 넣어둔 대로 작업 브랜치를 받아서 읽는다. `main`에 머지하면 이 우회는 필요 없어진다.

저장소 소스를 연결한 뒤 첫 자동 실행에서 신규 4건이 정상 적재됐다. 그 과정에서 확인된 것들:

- **스레드 맥락 보강이 실제로 효과가 있었다.** "AI 드라이브 배포되었습니다" 같은 한 줄 메시지도 부모 스레드를 읽어 배포 경위를 붙이니 뉴스가 됐다. 이 단계를 빼면 위클리가 맥락 없는 단문 모음이 된다.

## 10. 봇 명의 발송과 네트워크 정책 (2026-09-07)

위클리를 **확성기봇 명의**로 내보내려면 Slack Incoming Webhook이 필요하다. Slack MCP(`slack_send_message`)는 항상 쓸 수 있지만 **운영자 개인 계정 명의**로만 나가고, 슬랙이 본인 멘션 알림을 억제하기 때문에 전사 공지용으로는 약하다.

문제는 웹훅 도메인이 클라우드 세션의 egress 정책에 걸린다는 점이다.

```
kind:   connect_rejected
detail: gateway answered 403 to CONNECT
host:   hooks.slack.com:443
```

진단은 `curl -sS "$HTTPS_PROXY/__agentproxy/status"` 로 한다. `recentRelayFailures`에 차단된 호스트와 사유가 그대로 찍힌다. 정책 거부이므로 재시도하거나 우회하지 않는다.

### 환경마다 정책이 다르다

계정에 환경이 여러 개면 네트워크 정책도 각각이다. 확인은 `list_environments`.

| 환경 | hooks.slack.com |
| --- | --- |
| `env_01KNQLFBBCUbK2iw4D3EUVCx` (Default Cloud Environment) | 차단 |
| `env_01Rk69KYRBjm3TSL3hPL81ER` (Default — trusted network access) | 열림 |

**웹훅으로 발송하는 Routine은 열린 환경에서 만들어야 한다.** 차단된 환경에 만들면 실행은 "성공"으로 끝나면서 발송만 조용히 실패한다.

### 출근봇이 웹훅으로 잘 도는 이유

그 작업은 클라우드가 아니라 운영자의 맥에서 돌기 때문이다(스킬이 `/Users/mary/Desktop/...`에 CSV를 쓴다). 로컬에서 된다고 클라우드에서도 된다는 뜻이 아니다 — 새 봇을 만들 때 가장 걸리기 쉬운 함정이다.

### 연결 테스트는 GET으로

슬랙 웹훅은 GET에 대해 메시지를 게시하지 않고 400만 돌려준다. 채널에 아무것도 올리지 않고 터널만 확인할 수 있다.

```
curl -sS -o /dev/null -w '%{http_code}\n' <webhook_url>
```

`CONNECT tunnel failed, response 403` → 아직 차단. 정상 HTTP 코드 → 열림.

## 10. 3호에서 배운 것 (2026-09-18)

9/14~9/18 위클리를 확성기봇 명의로 처음 발행했다. 그 과정에서 굳어진 규칙들.

### 발송 — `ok`는 도착의 증거가 아니다

같은 본문을 최상위 `text` 필드로 두 번 보냈는데, 두 번 다 **`ok` / HTTP 200을 받고도 빈 메시지가 올라갔다.** 운영자는 빈 말풍선을 보고 있는데 봇은 보냈다고 보고하는 상태였다. `blocks`의 section에 담자 그대로 들어갔다.

```json
{"username":"확성기봇","icon_emoji":":mega:","unfurl_links":false,"unfurl_media":false,
 "text":"튜링 위클리 초안",
 "blocks":[{"type":"section","text":{"type":"mrkdwn","text":"<본문>"}}]}
```

최상위 `text`는 알림 미리보기용 한 줄로만 남긴다. section 하나의 상한은 3000자.

**보낸 뒤 반드시 `slack_read_channel(limit=1, response_format="detailed")`로 그 메시지를 되읽어 본문이 실제로 들어갔는지 확인한다.** 비어 있으면 다시 보낸다.

### 검수본은 발행과 같은 경로로 보낸다

검수 DM을 `slack_send_message`로 보냈더니 서식이 깨졌다. 그 도구는 **표준 마크다운**을 받아 슬랙 서식으로 변환하기 때문에, 웹훅용 mrkdwn을 넣으면 `> `가 인용이 아니라 글자로 남고 `*굵게*`가 기울임이 된다.

실제 발행물은 멀쩡했으니 겉보기엔 사소한 문제 같지만, **검수 화면이 발행물과 달랐다는 게 진짜 문제다.** 다른 것을 보고 승인하면 검수가 아니다. 그래서 검수도 웹훅 경로로 통일했다.

### 🏆는 자기 글 자기 📣도 포함한다

작성자와 찍은 사람이 같아도 빼지 않는다. 자기 팀 소식을 팀에 알린 것도 확성기를 든 것이고, 여기서 걸러내기 시작하면 정작 현장에서 소식을 물어오는 사람이 크레딧에서 빠진다. 그 주에 📣를 찍은 사람 **전원** — 예외 없음.

### 이미지 — 봇이 고르고 사람이 붙인다

Slack MCP에 파일 업로드 도구가 없고, 비공개 채널 파일 URL은 인증이 걸려 있어 `image_url` 블록으로도 안 뜬다. **봇이 스레드에 사진을 올릴 방법은 없다.**

다만 `slack_read_file`로 **이미지를 직접 열어볼 수는 있다**(10MB 제한). 그러니 링크 목록만 던지지 말고, 후보를 다 보고 "이 3장이 좋다"를 이유와 함께 골라준다. 파일명(`81488.jpg`)으로 지목하면 원문에서 바로 찾을 수 있다.

올리는 건 사람이 한다. 가장 빠른 길은 원문 메시지 `⋯` → **메시지 전달** → 위클리 스레드 — 다운로드 없이 첨부가 통째로 붙는다. 수십 MB짜리 동영상은 본문에 링크가 있으면 스레드에 안 올리는 편이 낫다.

### 찍은사람은 그 건의 `:mega:` 줄에서만

두 건의 `찍은사람` 값이 서로 뒤바뀐 채로 초안이 나갔다. 건마다 `slack_get_reactions`를 개별 호출하고, **그 응답의 `:mega:` 줄에서만** 이름을 가져온다. 다른 이모지를 찍은 사람, 본문에 멘션된 사람, 스레드 참여자, 작성자를 섞지 않는다.

크레딧이 이 제도의 연료라서, 한 건이라도 틀리면 팀이 바로 알아본다.
